# Prompt 设计文档

> 对应简历项目经历「AI Prompt 设计文档 / Prompt 优化」。
> 每个任务使用**独立角色 Prompt**,并做「系统指令 → 任务标记 → Schema 约束 → 示例」四层设计。
> 代码实现见 `app/prompts.py`,结构化解析与纠错重试见 `app/llm.py: llm_json`。

## 1. 设计原则

1. **角色隔离**:一个 Prompt 只做一件事(解析 / 评估 / 生成),避免角色混用导致输出漂移;
2. **约束输出 Schema**:所有结构化节点要求「只输出 JSON + 示例 Schema」,解析失败自动带纠错提示重试 1 次;
3. **RAG 上下文注入**:检索结果作为用户提示词注入(而非系统提示词),并要求「优先引用知识库、不臆造」,用于防幻觉与可归因;
4. **工具授权**:生成节点声明可用工具(高德/天气),由 LLM 决定是否调用(ReAct 语义,类 MCP function calling);
5. **自动降级**:LLM 输出不可用时,回到确定性模板行程,保证功能闭环。

## 2. Prompt 总览

| 节点 | 任务标记 | 输入 | 输出 |
| --- | --- | --- | --- |
| parse | `__TASK_PARSE__` | 用户自然语言 | JSON(TravelRequest) |
| evaluate | `__TASK_EVALUATE__` | 需求+知识库+天气+预算 | JSON(EvalReport) |
| generate | 无(PLAN_SYSTEM) | 需求+知识库+评估+工具 | Markdown 行程 |
| clarify | 无 | 缺失字段清单 | 一句追问话术 |

## 3. 关键 Prompt 摘录

### 3.1 需求解析(PARSE_SYSTEM 要点)

```
你是一名旅行需求分析助手,任务:__TASK_PARSE__。
从用户自然语言中提取结构化旅行需求。要求:
1. 只输出一个 JSON 对象,不要输出任何解释文字;
2. 未提及的字段填空字符串,不得臆造;
3. destination 必须给出具体城市/地点;
4. preferences 从标签中选择:美食、自然风光、历史文化...
JSON Schema 示例: {...}
```

设计要点:
- **任务标记** `__TASK_PARSE__` 使同模型可复用(代码中被替换为空串,真实调用不暴露);
- **负向约束**「不得臆造」是结构化节点的关键——缺失字段交给澄清分支处理;
- **枚举偏好标签**:可控枚举比自由文本更利于下游 RAG query 构造。

### 3.2 可行性评估(EVALUATE_SYSTEM 要点)

```
你是一名旅行可行性评估专家...
基于【用户需求】【知识库检索结果】【工具数据(天气等)】输出 JSON:
weather_ok / weather_summary / season_fit / budget_fit / crowd_note / risks / suggestions
```

设计要点:三源交叉(需求 × 知识库 × 实时天气)让评估有事实支撑;risks/suggestions 数组直接进入最终行程的「出行贴士」。

### 3.3 行程生成(PLAN_SYSTEM 要点)

```
你是一名资深旅行规划师...
每天输出: 上午/下午/晚上分段 + 餐饮推荐(人均) + 住宿建议(区域+价位)
末尾输出: 预算总览(分项) + 出行贴士
必须优先引用知识库检索结果;工具不可用时标注'部分信息来自知识库估算'
```

设计要点:输出结构用「条目清单」约束,比纯自由文风更容易保证每天都有景点/餐饮/住宿/预算;

## 4. 评估与迭代指标(简历中的「指标优化」)

| 指标 | 口径 | 优化手段 |
| --- | --- | --- |
| 召回率 | 检索结果覆盖目标城市案例 | seed 查询+城市软过滤 |
| 信噪比 | 无关于扰 chunk 占比 | 语义级预切片(景点/美食/住宿/预算/可行性)+ 中文感知二次切分,参考 `app/rag/chunker.py` |
| 准确度 | 行程信息与知识库一致性 | 强制引用知识库+来源标注+输出格式校验 |
| 稳定性 | 结构化解析成功率 | JSON Schema+失败重试+模板兜底 |
